## 模組一：高效能快取架構（Cache Architecture）

當系統讀取流量（QPS）過高、關聯式資料庫（RDB）面臨效能瓶頸時採用的緩存策略。

### 1. 核心讀寫模式
* **旁路快取模式（Cache-Aside Pattern）**
  * **讀取流程**：應用程式先查 Cache。若命中（Cache Hit）則直接回傳；若未命中（Cache Miss），則查 Database，並將結果非同步或同步**回填（Backfill）**至 Cache，再回傳。
  * **寫入流程**：先更新 Database，再**使快取失效（Invalidate / Delete Cache）**，避免雙寫不一致。
* **存活時間（TTL, Time-To-Live）**
  * 資料在快取中的有效期限，逾期由快取引擎自動逐出（Eviction），達到資料最終一致性（Eventual Consistency）並釋放記憶體。

### 2. 快取三大經典異常防禦（Cache Anomalies & Mitigations）
* **快取擊穿（Cache Breakdown / Hotspot Invalidation）**
  * **現象**：單一極度熱點（Hot Key）在過期瞬間，大量併發請求直接穿透至資料庫。
  * **解法**：**互斥鎖（Mutex Lock / Distributed Lock）**。僅允許第一個取得鎖的請求查詢資料庫並回填快取，其餘請求排隊等待或重試讀取快取。
* **快取穿透（Cache Penetration）**
  * **現象**：查詢**根本不存在**的資料（惡意攻擊或錯誤 ID），快取與資料庫皆無資料，導致每次請求均直擊資料庫。
  * **解法**：
    1. **快取空值（Cache Null Object）**：查詢為空時，仍寫入空值（如 `null` 或 `"{}"`）至快取，並賦予極短 TTL。
    2. **布隆過濾器（Bloom Filter）**：在存取快取前透過概率型資料結構快速過濾不存在的 Key。
* **快取雪崩（Cache Avalanche）**
  * **現象**：大量快取的 TTL 設定相同，在同一時間點集體過期，或快取服務節點故障，造成流量全部轉移至資料庫引發連鎖崩潰。
  * **解法**：**TTL 隨機擾動（Jitter / Random TTL）**。在基礎過期時間上加上隨機值（如 24h + 隨機數秒/分），打散過期時間點。

## 模組二：非同步處理與訊息佇列（Message Queue & Asynchronous Processing）

用於解決長耗時任務阻塞主執行緒、降低系統耦合度（Decoupling）與應對突發流量。

### 1. 核心機制
* **解耦（Decoupling）與非同步化（Asynchronous Processing）**
  * 主交易流程（如扣款、建立訂單）同步完成並立即響應客戶端；週邊耗時任務（寄送郵件、呼叫外部物流）封裝為訊息投遞至訊息佇列（Message Queue），由背景工作行程（Background Worker）進行消費。
* **削峰填谷（Traffic Shaping / Rate Leveling）**
  * 利用佇列緩衝突發流量，背景 Worker 依照資料庫或第三方能承受的固定速率平穩處理。

### 2. 可靠性與容錯機制（Fault Tolerance）
* **指數退避重試（Exponential Backoff Retry）**
  * 外部依賴短暫不可用時，重試間隔應隨失敗次數呈指數級遞增（例如：1s, 2s, 4s, 8s...），避免密集重試造成目標系統次生雪崩。
* **死信佇列（Dead Letter Queue, DLQ）**
  * 當訊息重試達上限仍無法處理（毒訊息 Poison Message），將其自正常佇列剔除並轉移至死信佇列進行隔離，避免阻塞佇列頭部（Head-of-Line Blocking），並支援告警與事後人工介入重放（Replay）。
* **冪等性設計（Idempotence）**
  * **核心定義**：同一操作重複執行多次，產生的系統狀態與業務結果皆與執行一次完全相同。
  * **解法**：**冪等鍵（Idempotency Key / Unique Transaction Token）**。每次操作附帶全域唯一識別碼（如訂單編號），處理前先依此 Key 檢查執行歷史，防止網路超時（Network Timeout）觸發重試所導致的重複扣款或重複出貨。

## 模組三：水平擴展與無狀態認證（Stateless Architecture & Auth）

消除單點故障（SPOF），讓應用伺服器具備動態水平擴展能力（Horizontal Scaling）。

### 1. 架構典範轉移
* **有狀態架構（Stateful Architecture）**
  * 使用者 Session 保存在單一伺服器記憶體中。經負載平衡器（Load Balancer）輪詢後，若請求被分派至不同伺服器，會因 Session 遺失而被迫重新登入。
* **無狀態架構（Stateless Architecture）**
  * 伺服器本身不保留任何客戶端連線狀態，所有實例（Instances）對等，任何節點均可處理任何請求。

### 2. 認證演進方案
* **集中式 Session 儲存（Centralized Session Store）**
  * 所有應用伺服器共享外部集中快取（如 **Redis Session Cluster**），保留對 Session 的即時控制權（即時剔除用戶）。
* **無狀態權杖（Stateless Token - JWT, JSON Web Token）**
  * 伺服器利用私鑰（Secret Key）對 Payload 進行數位簽名（HMAC / RSA）。客戶端發送請求時附帶 Token，伺服器僅需進行**本地驗簽（Local Signature Verification）**，完全不查資料庫。
  * **致命缺陷**：Token 發行後無法主動吊銷（Revocation），修改權限或封鎖帳號難以即時生效。
* **雙權杖機制（Dual-Token Pattern）**
  * **存取權杖（Access Token）**：短生命週期（5 ~ 15 分鐘），無狀態驗簽，追求極致效能。
  * **重新整理權杖（Refresh Token）**：長生命週期（7 ~ 30 天），受控儲存於後端（Redis/DB）。當 Access Token 過期時用於換發新 Token；管理員停權時，只需刪除此 Token 即可在數分鐘內徹底終止其連線。

## 模組四：高併發控制與資料一致性（Concurrency & Data Consistency）

面對多個執行緒或請求在同一毫秒存取同一份共享資源時的防禦技術。

### 1. 併發異常
* **競態條件（Race Condition）**
  * 多個進程同時讀取相同資料，並基於讀取到的舊值進行運算與回寫。
* **超賣（Overselling / Over-allocation）**
  * 因「檢查（Check）」與「更新（Act）」非原子操作（Time-of-Check to Time-of-Use, TOCTOU），導致實體資源已被扣盡，但多個請求仍通過校驗繼續寫入。

### 2. 資料庫鎖定控制（Locking Mechanisms）
* **悲觀鎖（Pessimistic Locking）**
  * **作法**：透過交易搭配排他鎖（`SELECT ... FOR UPDATE`），在讀取時即將該列（Row）鎖定，其他請求強制阻塞等待。
```SQL
START TRANSACTION;

-- 後面加上 FOR UPDATE，這就是把這筆資料「鎖定」！
SELECT stock FROM products WHERE id = 1 FOR UPDATE;

-- 這時候 User B 也下了 SELECT ... FOR UPDATE，他會被資料庫「卡住（等待）」，直到 User A 結束！

UPDATE products SET stock = stock - 1 WHERE id = 1;

COMMIT; -- 提交事務，釋放鎖定。這時 User B 才會被喚醒，但他一讀取發現 stock 已經是 0 了！
```

  * **代價**：併發量極大時，大量請求排隊等待釋放鎖，導致**資料庫連線池耗盡（Connection Pool Exhaustion）**與 CPU 滿載。

* **樂觀鎖 / 條件更新（Optimistic Locking / Conditional Atomic Update）**
  * **作法**：不加鎖，直接依賴資料庫底層的原子操作與行級鎖（Row Lock）：
    ```sql
    UPDATE products SET stock = stock - 1 WHERE id = ? AND stock > 0;
    ```
  * **原理**：將檢查條件（`stock > 0`）與扣減運算（`stock - 1`）融合成單一**原子操作（Atomic Operation）**。若影響列數 `affected_rows == 0` 即視為併發競爭失敗。

### 3. 超高流量終極解法
* **記憶體預扣減（In-Memory Pre-allocation with Redis）**
  * 將高頻搶扣的「熱點資料」由 RDB 移至 **Redis**。
  * 憑藉 Redis 的**單執行緒事件循環（Single-Threaded Event Loop）**與記憶體操作特性，天然保證指令的**原子性（Atomicity）**（如 `DECR` 或 Lua Script）。
  * 記憶體扣減成功者才獲得向後端隊列投遞訂單的資格，在最前端過濾掉 99% 的無效資料庫寫入流量。
